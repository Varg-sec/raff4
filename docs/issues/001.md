# Pin the conformance baseline and runnable reference corpus

Local ID: AFF4-001

Type: HITL · Area: foundation

## What to build

Establish the exact format profiles the first release promises, and a reproducible fixture runner that reports coverage rather than assuming every implementation agrees.

## Acceptance criteria

- [ ] Pin commits and content digests for standards, canonical images, pyaff4, c-aff4 and aff4tools; record retrieval and redistribution terms.
- [ ] Find and review the current in-progress AFF4 base document as well as AFF4-L; the base PDF and draft must not silently be treated as interchangeable.
- [ ] Map every normative requirement to a reader/writer test or explicit unsupported capability; identify mandatory versus optional requirements.
- [ ] Resolve draft namespace, dataSteam/dataStream spelling, inline size units, SHAKE output length and signature encoding ambiguities against pinned images; unresolved items remain explicit release blockers.
- [ ] Run one fixture through an independent oracle and store expected object identifiers, content digest and metadata; missing fixtures produce a visible blocked result, never a pass.
- [ ] Maintainer confirms baseline, license, Rust/Python support policy and first-release scope before downstream conformance claims.

## Blocked by

None — can start immediately.

## Evidence and delivery

Use the pinned baseline established in AFF4-001 and the source index in docs/design.md. Add an end-to-end fixture demonstrating this capability, record unsupported cases, and update the conformance matrix. Bindings must delegate format behavior to the Rust core.
